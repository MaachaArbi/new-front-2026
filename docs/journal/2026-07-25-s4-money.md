## Résumé

Le noyau `Money` est écrit dans `src/shared/money/` : type `bigint` en unités
mineures, immuable, indissociable de sa devise ; type `Rate` distinct pour les
taux `pricing_*` ; registre de devises provisoire (source de `minor_unit`) ;
formatage et parsing localisés via `Intl` ; conversion API ; composant de saisie
`MoneyInput`. L'outillage de test (Vitest + Testing Library) est installé, **67
tests / 141 assertions**, tous verts. Une règle ESLint fait échouer le lint sur
`toFixed` et sur la multiplication/division en clair d'un montant par 100/1000,
avec exception pour le noyau. Tout se vérifie en ligne de commande.

Vague **entièrement indépendante du backend** (logique pure, aucun réseau). La
forme réelle des montants dans les DTO backend a été **lue** avant d'écrire la
conversion (`/home/ubuntu/ostravel`, sans y écrire).

Fichiers `src/shared/money/` : `money.ts`, `rate.ts`, `rounding.ts`,
`currency-registry.ts`, `format.ts`, `parse.ts`, `locale-separators.ts`,
`api.ts`, `money-input.tsx`, `index.ts` + 8 fichiers de test.

## Ce qui a été fait

### Le type (§4.1)

`Money = { amount: bigint, currency: string }`, immuable, **marqué** (brand
nominal). `bigint` en unités mineures : exact au-delà de 2^53, et interdit
mécaniquement tout mélange flottant. Addition/soustraction/comparaison **exigent
la même devise** et lèvent `CurrencyMismatchError` sinon. Reflet du VO backend
`App\Shared\Domain\ValueObject\Money`.

`Rate` (taux/marge `pricing_*`, `NUMERIC(12,4)`) est un **type distinct** :
`scaled: bigint` × 10^4, marque propre → **impossible à la compilation** de le
passer là où un `Money` est attendu.

### La source du minor_unit (§4.2)

`currency-registry.ts` — registre local **clairement marqué provisoire**.
Couvre 12 devises : TND, LYD, JOD, **KWD, BHD, OMR** (3 décimales) + EUR, USD,
MAD, DZD, SAR, AED (2). Remplaçable par l'API via `loadCurrencyRegistry(...)`
**sans changer un appelant** (tous passent par `getCurrency`/`getMinorUnit`).
Devise inconnue → `RangeError` (jamais de facteur 10 silencieux). Ajouté au
backlog : « remplacer le registre local par le référentiel API ».

### Les opérations (§4.3)

Construction depuis unités mineures (`bigint`/`string`/`number` sûr) et depuis
saisie ; add/subtract ; `multiplyByInteger` (exact) ; `multiplyByRate` (**arrondi
explicite obligatoire**) ; `divide` (arrondi explicite) ; `split` (équiparti) et
`allocate` (pondéré, `booking_payer_split`) **sans perte** ; comparaisons, zéro,
signe, négation, absolu. 7 stratégies d'arrondi (`rounding.ts`), gérant le signe.

**Conversion API** (`api.ts`) — alignée sur la forme **réelle** vérifiée dans les
DTO : `amountMinor` (entier) + `currencyCode` (string sœur), jamais imbriqués,
pas de `minorUnit` exposé. `fromApi` refuse un `number` non entier-sûr ;
`toApi`/`toMinorUnitsString` émettent en string (sans perte).

### Le formatage (§4.4)

`format(money, locale)` via `Intl.NumberFormat`, décimales pilotées par la
**devise**, séparateurs/symbole par la **locale**. **Exact au-delà de 2^53** :
jamais de `Number(amount)` — la partie entière est formatée comme `bigint`, la
fraction chiffre par chiffre, le symbole/signe repris de `formatToParts`.
**Chiffres arabo-indiens : non tranché** (ADR-F04) — on reste sur le défaut
d'`Intl` (en locale `ar`, chiffres arabo-indiens), partie entière et fraction
passant toutes deux par `Intl` pour rester cohérentes. Signalé ici.

### Le composant de saisie (§4.5)

`MoneyInput` (dans `src/shared/money/`), bâti sur le `Input` de `src/shared/ui/`
— **aucune nouvelle dépendance**. Accepte le séparateur décimal de la locale,
refuse trop de décimales (`aria-invalid` + message relié `aria-describedby`),
libellé associé (`htmlFor`/`id`), `role="alert"`. Aucune classe directionnelle
physique. Le champ affiche une **string éditable** (sans symbole), pas le format
monétaire — sinon l'aller-retour saisie casserait.

### La règle ESLint (§5)

Ajoutée dans `eslint.config.js`, sur le modèle de la règle RTL de S3b
(`no-restricted-syntax`). Fait échouer le lint sur : `.toFixed(` ; et
multiplication/division littérale par `100`/`1000` d'une variable dont le nom
évoque un montant (`amount|montant|total|price|prix|solde|balance`) — faux
positif assumé (« mieux qu'un montant faux »). **Exception** : le noyau
`src/shared/money/**` (la règle RTL y **reste** active).

**Tests que la règle mord (exécutés)** :
- `toFixed(2)` injecté dans `use-document-title.ts` (hors noyau) → lint échoue
  (1 error, exit 1), message ADR-F07. Retiré, lint repasse à 0.
- `toFixed(2)` injecté **dans** le noyau (`rounding.ts`) → **toléré** (exception).
- `ml-2` injecté dans `money-input.tsx` → lint échoue (RTL toujours actif dans
  le noyau). Retiré.

### Les tests (§6)

Vitest + `@testing-library/react` + `@testing-library/jest-dom` + `jsdom`
installés (rien d'autre). Config **séparée** `vitest.config.ts` (évite tout
conflit avec `vite.config.ts`, §10) ; `globals: true` pour l'auto-cleanup de
Testing Library. Fichiers de test **exclus** de `tsconfig.app.json` : `tsc -b` et
`npm run build` restent centrés sur le code applicatif (dist vide garanti),
Vitest gère les tests via esbuild. Script `npm run test`.

Assertions des cas limites **écrites à la main**, résultat déterminé avant de
lancer le code. Couverture des cas obligatoires : TND 3 déc., EUR 2 déc., même
bigint/devises différentes, addition inter-devises échoue, répartition sans
perte (100,000 TND en 3, 0,001 TND en 2), négatif/zéro, au-delà de 2^53,
saisie fr « 1 240,500 » = en « 1,240.500 », trop de décimales rejetée, formatage
dans les trois locales.

## Dérives & corrections

**Obligatoire, même vide.** Ci-dessous, tout ce qui a dû être deviné, tout écart,
toute correction.

### 1. Numérotation de vague incohérente avec le backlog — SIGNALÉ, non « corrigé »

Le prompt intitule cette vague **« S4 — Noyau Money »**. Or `docs/STATUS.md` et
`docs/backlog/todo.md` (état S3c) planifiaient **S4 = consolidation i18n
FormatJS/react-intl** et **S7 = Noyau Money**. Le prompt de S3b annonçait aussi
« S4 — i18n & RTL ».

Le **contenu** du prompt est sans ambiguïté (Money + Vitest + règle `toFixed`) :
je l'ai exécuté tel quel. Je n'ai **pas** silencieusement renuméroté ni fait
autre chose. J'ai avancé la ligne « Noyau Money » à cette vague dans le backlog
et STATUS, en le **signalant** ici. La consolidation i18n/react-intl (l'ancienne
« S4 ») **reste à faire** et n'a pas été touchée. → à réconcilier par le chat
pilote : soit Money devient officiellement S4, soit renuméroter.

### 2. « Reglements » (prompt/reference) vs « Settlement » (backend réel)

Le prompt (§3) et la reference parlent du module « Reglements » et de
`ref_currency`. Le backend réel nomme le module **`Settlement`** (+
`CashManagement`) ; la VO est `App\Shared\Domain\ValueObject\Money`. `ref_currency`
et `booking_payer_split` existent bien. Aucune règle métier déduite : j'ai lu le
code réel et aligné la conversion API sur les DTO **effectifs** (`Settlement`,
`Booking`). Signalé, non corrigé dans la reference (lecture seule).

### 3. Montants sérialisés en nombre JSON — risque de contrat SIGNALÉ

Les DTO backend émettent `amountMinor` en **nombre JSON** (pas string). Au-delà
de 2^53, `JSON.parse` corrompt la valeur **avant** Money. Ce n'est pas ambigu
(c'est clairement un `number`), mais c'est **risqué**. Parade front : `fromApi`
refuse un `number` non entier-sûr (lève au lieu de propager). Vraie parade côté
producteur → **demande backend** `docs/demandes-backend/2026-07-25-montants-json-string.md`
+ backlog. Non contourné.

### 4. Number Field de ReUI non tiré — choix assumé, conforme au périmètre

ADR-F07 mentionne « composant bâti sur le Number Field de ReUI ». Mais le prompt
§4.5 impose **aucune nouvelle dépendance** et §7 interdit d'**ajouter un composant
à `src/shared/ui/`**. Tirer le Number Field violerait les deux. J'ai donc bâti
`MoneyInput` sur le `Input` **existant** de `src/shared/ui/`. Écart au libellé
d'ADR-F07, mais conforme aux contraintes explicites du prompt ; signalé.

### 5. Bug attrapé pendant l'écriture des tests (auto-correction)

Le brouillon initial de `MoneyInput` initialisait le champ avec `format()` — qui
**porte le symbole** (« €5.00 ») : un aller-retour de saisie l'aurait rejeté
comme parasite. Corrigé par un `toEditableString` (string éditable sans symbole,
« 5.00 »/« 5,00 »). Attrapé parce que l'assertion du test a été écrite **avant**
de constater le comportement — exactement le garde-fou visé au §6.

### 6. Valeur attendue recalculée à la main (répartition pondérée)

Pour `allocate(1000, [1,2,3])` j'avais d'abord noté `[166,334,500]` ; le calcul
du plus grand reste donne `[167,333,500]` (résidus 4/6 > 2/6 > 0 → l'unité va à
l'indice 0). Corrigé **avant** exécution. La somme reste exacte dans les deux
cas ; seule la répartition du reste changeait.

### 7. `globals: true` ajouté à Vitest — nécessaire, pas cosmétique

Sans lui, l'auto-cleanup de `@testing-library/react` ne s'enregistre pas (pas de
`afterEach` global) : les rendus s'accumulent et `getByLabelText` renvoie un
élément périmé. Diagnostiqué par isolation (un test seul passait, la série
échouait). Corrigé.

### 8. Vulnérabilités npm préexistantes — NON traitées (hors périmètre)

`npm ci` signale 2 vulnérabilités « high » sur **`react-router`** (advisory RSC
mode CSRF) — dépendance **préexistante** (S3b), **pas** de mes ajouts, et l'app
est une SPA sans mode RSC. Je n'ai **pas** lancé `npm audit fix` (bump de version
= hors sujet S4, risque de non-déterminisme de `npm ci`). Ajouté au backlog.
